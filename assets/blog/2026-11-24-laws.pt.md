# Regras que NINGUÉM quebra

Cada vez mais código é escrito por agentes de programação, e logo a maior parte dele será. O Hive não é exceção: eu o construo com um ao meu lado. Isso muda o que um projeto precisa da sua linguagem: um jeito de declarar as poucas regras que nunca podem ser quebradas, e fazer a build recusar toda mudança que as quebre, não importa quem ou o que a escreveu. No Hive, isso é uma lei.

## Pedir com educação não basta

Todo projeto tem regras inegociáveis. Um cliente só vê os próprios dados. Um desconto nunca deixa um preço abaixo de zero. Uma reserva cancelada continua cancelada. Até hoje, essas regras viveram em lugares que só pedem: um comentário, uma revisão de código, um teste que tenta meia dúzia de casos e, mais recentemente, um `AGENTS.md` que pede ao robô, com toda a educação e muita manipulação emocional (apesar da sua natureza sem emoções), que por favor não faça aquilo.

Nada disso se sustenta quando ninguém está olhando. Quem revisa passa os olhos pelo quadragésimo arquivo de um pull request. Testes unitários só pegam os cenários em que alguém já pensou. Um agente no meio de uma tarefa longa lê a instrução e, três passos depois, escreve justamente a consulta que vaza as notas de outro cliente. Não por maldade: nada o impediu.

Uma lei é uma regra que o compilador prova para todo valor possível antes de construir qualquer coisa. Se ele não consegue provar, o programa não compila, e nada deixa um programa aceitar uma lei que não foi provada. A regra deixa de ser algo que você espera que todos lembrem e vira algo que ninguém consegue contornar.

## Como: uma regra sobre os seus dados

Digamos que toda consulta à tabela `notes` precise pertencer a uma conta. Escreva isso uma vez, como uma lei sobre a tabela:

```hive
type Account {
	id: Int
}

type Note {
	body: Str
}

law ownNotesOnly(account: Account) for table notes {
	account_id = {account.id}
}

query search(account: Account, word: Str): Note[dyn] {
	SELECT body FROM notes WHERE body LIKE {word}
}
```

A consulta `search` acima esqueceu a conta. Todo mundo já fez isso. A build não deixa passar:

```
$ hive check notes.hive
notes.hive:13: in `search`: this query reads `notes` without the filter law `ownNotesOnly` keeps on it
    its WHERE has to carry `account_id = {account.id}`
```

O erro diz qual é a regra e o que está faltando, que é exatamente o que um agente precisa para corrigir o próprio erro. A regra não depende de o agente ter lido o arquivo certo; depende de o código compilar.

## Como: uma regra sobre os seus tipos

Uma lei escrita dentro de um tipo é cumprida por todo valor desse tipo, em todo lugar onde um é criado ou alterado:

```hive
type Percent {
	value: Int

	law inRange(p: Percent) {
		assert p.value >= 0 && p.value <= 100
	}

}

func double(p: Percent): Percent {
	return Percent(p.value * 2)
}
```

```
$ hive check percent.hive
percent.hive:11: in `double`: cannot prove `Percent.inRange` for this `Percent(...)`: nothing here shows `2 * p.value <= 100`
    known: 0 <= 2 * p.value; 0 <= p.value; p.value <= 100
    guard it, so that the law holds here
```

Em troca, nenhum código que recebe um `Percent` precisa conferi-lo de novo, e um decodificador recusa um valor que quebre a lei já na leitura.

## O que ela não faz

Dá para simplesmente apagar a lei? Dá. Mas isso vira uma linha num diff que diz, com todas as letras, "esta regra não vale mais", e isso é muito mais difícil de passar batido numa revisão do que um bug enterrado no quadragésimo arquivo.

Também há limites. Uma lei não acompanha um laço que não seja `for each` ou um laço de contagem, nem uma função de um arquivo Go importado, e não prova nada sobre aritmética de `Float`. SQL montado em tempo de execução com `hive.sql.unsafe` não é verificado. O Hive ainda não chegou à 1.0, e as leis são a parte mais nova dele.

Se o seu projeto tem uma regra pela qual você poria a mão no fogo, escreva-a onde o compilador consiga ler. O tour mostra como: [Leis](tour:Laws) e [Leis sobre uma tabela](tour:Laws on a table).
